# 결과서 작성 규칙

`result.md` 는 이 규칙을 따른다. 문체는 `docs/answer-guide.md` 를 따른다 (한 문장 한 사실, 결론 먼저).

## 1. 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| 판정 근거를 상세히 쓴다 | 읽는 사람이 코드를 열지 않고도 왜 그 판정인지 이해해야 한다. 표 한 칸에 근거 한 줄로 압축하지 않는다 | 압축된 근거는 전제 지식이 없으면 뜻이 통하지 않는다 (사용자 피드백) |
| 발견 사항과 수정 방법을 한 섹션에 쓴다 | 별도 "수정 제안" 절에 코드·설정 수정 방법을 모으지 않는다. 발견 사항 섹션 끝에 수정 방법과 수정 후 확인 방법을 쓴다 | 문제와 해결을 위아래로 오가며 읽지 않게 한다 (사용자 피드백) |
| 같은 수정으로 해결되는 발견 사항은 한 섹션으로 묶는다 | 묶은 섹션은 `SEC-n` 으로 부른다. 안의 발견 사항은 `CODE-n`·`CONF-n` ID 를 유지한다 | 수정 방법을 한 번만 쓰고, 추적용 ID 는 남긴다 |
| 의존성 수정 제안은 검증을 통과한 것만 쓴다 | `verify_patch.py` 판정이 통과인 제안만 확정한다. 검증 결과는 의존성 수정 제안 바로 아래에 둔다 | 제안 버전으로 올려도 문제가 없는지 확인할 수 있어야 한다 (사용자 요청) |

## 2. 결과서 구조

```markdown
# Result: 보안 점검

## 요약
- 점검 모듈, 우선순위별 건수(P1/P2/P3)
- 가장 시급한 조치 1~3개 (SEC-n·DEP-n ID 와 한 줄 설명)

## 계획 대비 변경 사항
- 해석 실패 모듈, 건너뛴 항목, 실행하지 못한 검증과 이유 (없으면 "없음")

## 의존성 취약점
| 우선순위 | 패키지 | 현재 버전 | 영향 모듈 | 심각도 | 해소 버전 | 영향도 근거 |

### DEP-n [P1] <제목>          ← P1 의존성 취약점만 상세 블록 (3절 형식)

### 런타임 미포함 (core-lib 단독, 프론트엔드 빌드 도구)

## 의존성 수정 제안
- Boot·Spring Cloud·직접 지정 버전 표 (모듈별)
- build.gradle 변경 예시 (diff 블록), 프론트엔드 변경
- 전체 변경: verify/proposal.diff, 제안 파일: proposal/

### 제안 검증 결과
- verify/report.md 판정 요약 표 (기대 버전, 취약점 전후, 컴파일·테스트·프론트엔드 회귀)
- major·minor 변경 호환성 표 (의존성, 변경, 판정, 근거)
- 런타임 확인 필요 항목

## 코드·설정 취약점
- 발견 사항 블록의 항목 순서 안내 (배경·문제·확인 근거·공격 시나리오·영향·공격 조건)

### 요약
| 섹션 | 우선순위 | 모듈 | 내용 | 포함 발견 사항 |

### SEC-1 [P1] <무엇이 왜 위험한지 한 문장>
포함: CODE-1 (P1), CODE-3 (P2) ...
(공통 배경이 있으면 여기에)
#### CODE-1 [P1] <제목>
#### CODE-3 [P2] <제목>
#### SEC-1 수정 방법
#### SEC-1 수정 후 확인 방법

### SEC-n [P3] 기타 정리 항목
| 발견 사항 | 위치 | 문제 | 수정 방법 | 수정 후 확인 방법 |

### 양호 항목
| 영역 | 항목 | 확인 내용 |

## 변경 파일
- 없음 (제안만 작성, 제안 파일은 proposal/ 에 있음)

## 검증
- 실행한 스크립트, 조회 시각, 조회 출처(OSV, Maven Central, 참고 URL)

## 후속 작업
- 수정 적용 후 재점검, 런타임 확인 항목, 배포 구성 확인 항목, 판정 보류 항목
```

## 3. 발견 사항 블록 (P1·P2)

| 항목 | 쓰는 내용 |
|---|---|
| 위치 | 모듈 기준 `파일:줄` |
| 배경 | 해당 기능이 원래 어떻게 동작하도록 설계되었는지. 다른 모듈과의 관계 (예: gateway 가 검증하고 서비스는 헤더를 믿는다) |
| 문제 | 설계와 실제 코드가 어디서 어긋나는지. 목록 한 줄에 사실 하나 |
| 확인 근거 | 판정에 쓴 실제 코드 발췌. 코드 블록에 `// 파일:줄` 주석을 단다. 라이브러리 동작에 기대는 판정은 라이브러리 소스도 발췌한다 |
| 공격 시나리오 | 공격자가 밟는 단계를 번호 목록으로 쓴다. 실제 API 경로를 쓴다 |
| 영향 | 공격이 성공하면 공격자가 얻는 것. 노출되는 데이터 항목을 구체적으로 쓴다 |
| 공격 조건 | 인증 필요 여부, 외부 노출 여부. P1 이 아닌 이유가 조건에 있으면 그 이유를 쓴다 |

상황에 따라 더 쓰는 항목:
- **현재 영향이 제한적인 이유** + **위험해지는 조건**: 지금은 영향이 작지만 코드·설정이 바뀌면 위험해지는 항목
- **판정 보류 이유**: 실제 실행으로만 확정되는 항목
- 다른 발견 사항과 이어지면 ID 로 연결한다 (예: CODE-2 로 얻은 정보가 CODE-10 공격에 쓰인다)

## 4. 수정 방법과 수정 후 확인 방법

**수정 방법**
- 번호 목록으로 쓴다. 단계마다 어느 발견 사항을 해결하는지 괄호로 적는다 (예: `(CODE-1·3)`).
- 바꿀 파일과 위치를 쓴다. 필요하면 예시 코드·설정을 코드 블록으로 붙인다.
- 기존 데이터·호출부에 영향이 있으면 이전 방법을 함께 쓴다 (예: 기존 해시 재해시, Feign 경로 동시 변경).
- 예시 코드에 쓰는 API 는 실제로 있는지 라이브러리 소스로 확인한다.

**수정 후 확인 방법**
- 번호 목록으로 쓴다. 각 단계는 실행할 요청이나 확인할 값을 구체적으로 쓴다.
- 취약점이 막혔는지 확인하는 단계와, 정상 기능이 유지되는지 확인하는 단계를 모두 넣는다.

## 5. P3·양호 항목

- P3 는 SEC 섹션 하나에 표로 묶는다. 열: 발견 사항, 위치, 문제, 수정 방법, 수정 후 확인 방법.
- 양호 항목은 영역(코드·설정·프론트엔드)별로 확인 내용을 한 줄씩 표로 남긴다.

## 6. 예시 (발췌)

````markdown
### SEC-1 [P1] `X-User-Id` 헤더를 위조해 다른 사용자로 행세할 수 있다

포함: CODE-1 (P1), CODE-3 (P2), CODE-4 (P2)

#### CODE-1 [P1] gateway 가 `X-User-Id` 를 덮어쓰지 않고 덧붙인다

- **위치**: gateway `src/main/java/.../JwtAuthFilter.java:53-55`
- **배경**
  - gateway 가 JWT 를 검증하고, 토큰 속 사용자 ID 를 `X-User-Id` 헤더에 담아 서비스로 넘긴다.
  - customer·core-data 는 `X-User-Id` 헤더 값을 "로그인한 사용자"로 믿는다.
- **문제**
  - gateway 는 클라이언트가 보낸 `X-User-Id` 를 지우지 않는다.
  - gateway 는 검증한 사용자 ID 를 기존 값 뒤에 덧붙인다.
  - 서비스는 헤더의 첫 번째 값(클라이언트 값)을 읽는다.
- **확인 근거**
  ```java
  // JwtAuthFilter.java:53-55
  ServerRequest.from(request).header("X-User-Id", userId)   // 덧붙이기
  // spring-webmvc 7.0.6 DefaultServerRequestBuilder.java:127
  this.headers.add(headerName, headerValue);                 // set 이 아니라 add
  ```
- **공격 시나리오**
  1. 공격자가 가입·로그인해 자기 JWT 를 받는다.
  2. 공격자가 `X-User-Id: 피해자아이디` 를 붙여 `GET /customer/api/customers/me` 를 호출한다.
  3. customer 는 피해자 정보를 돌려준다.
- **영향**: 피해자의 이름, 생년월일, 복호화된 전화번호·이메일 조회. 피해자 명의 탑승자 등록·삭제.
- **공격 조건**: 아무 계정의 JWT (가입은 공개). gateway 외부 노출.

#### SEC-1 수정 방법

1. gateway 에서 모든 요청의 `X-User-Id` 를 먼저 지운다. 공개 경로 요청도 포함한다 (CODE-1·3).
2. 인증된 요청에는 `headers(h -> h.set(...))` 로 넣는다 (CODE-1).
3. 서비스 포트를 외부에서 막는다 (CODE-4).

#### SEC-1 수정 후 확인 방법

1. 계정 A 의 토큰과 `X-User-Id: B` 로 `GET /customer/api/customers/me` 를 호출해 A 의 정보가 나오는지 확인한다.
2. 서비스 포트로 직접 요청해 연결이 거부되는지 확인한다.
````
